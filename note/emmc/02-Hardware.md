## 2.1 MMC 总线协议

### 从物理层说起

MMC 总线由三组信号线组成：

```
Host (SDMMC2)                     eMMC
┌────────────────┐               ┌──────────┐
│                │──── CLK ─────→│          │
│   SDMMC        │←─── CMD ─────→│  eMMC    │
│   控制器       │←─── DAT[7:0] ─→│  芯片    │
│                │──── RST_n ────→│          │
│   (PL180)      │               │          │
└────────────────┘               └──────────┘
```

| 信号 | 方向 | 作用 |
|------|------|------|
| CLK | Host → Device | 时钟，所有信号在时钟沿采样 |
| CMD | 双向 | 命令 + 响应，同一条线分时复用 |
| DAT[7:0] | 双向 | 数据传输，可配 1/4/8 位 |
| RST_n | Host → Device | 硬件复位，低电平有效 |

**上电时序要求**：电源稳定后，eMMC 需要至少 74 个时钟周期才能开始接受第一条命令。这就是内核初始化代码中 `mmc_power_up()` 里 msleep 和发 CMD0 之间那些 delay 的原因。

### 命令在线上长什么样

一条命令在 CMD 线上传输时，是一个 48 位的串行帧：

```
CMD 线: [0] [1] [命令索引(6)] [参数(32)] [CRC7(7)] [1]
         ↑   ↑                                     ↑
       起始 传输                                  结束
       位   位=1                                  位
```

这 48 位的含义：

| 字段 | 长度 | 作用 |
|------|------|------|
| 起始位 | 1 bit | 固定为 0，总线空闲时 CMD 线是高电平 |
| 传输位 | 1 bit | 1 = 命令（Host→Device），0 = 响应（Device→Host） |
| 命令索引 | 6 bits | 命令号，CMD0~CMD63 |
| 参数 | 32 bits | 命令参数，每个命令的定义不同 |
| CRC7 | 7 bits | 校验前面的 40 bits（不包含起始/结束位） |
| 结束位 | 1 bit | 固定为 1 |

**实际例子：** CMD9（SEND_CSD）的作用是让 eMMC 返回 CSD 寄存器内容。Host 在 CMD 线上发 `0x49`（CMD9 的命令索引 = 9，传输位 = 1），参数填 RCA。eMMC 收到后在 CMD 线上返回 136 位的响应。

### 响应的三种常见格式

MMC 协议定义了 5 种响应类型（R1~R5），最常用的是三种：

**R1 响应（常规状态响应）：** 47 位，和命令帧格式基本一致，多了一个 32 位的状态字

```
CMD 线: [0] [0] [命令索引(6)] [状态(32)] [CRC7(7)] [1]
                ↑               ↑
            响应类型标志   卡当前状态 + 错误标志
```

ATK 板调试时最常看到这个响应——每次发完 CMD13（SEND_STATUS）后返回的就是 R1，其中状态字告诉你卡的当前状态（Tran、Data、Rcv 等）和是否有错误发生。

**R2 响应（CID/CSD 寄存器）：** 136 位，分 4 段返回

用于 CMD2（ALL_SEND_CID）和 CMD9（SEND_CSD）。eMMC 返回完整的 128 位寄存器内容 + 16 位 CRC。内核通过 `readl(base + SDMMC_RESP0)` ~ `readl(base + SDMMC_RESP3)` 四次读取这 128 位。

**R3 响应（OCR 寄存器）：** 48 位

用于 CMD1（SEND_OP_COND）。返回卡的 OCR 寄存器内容，告诉 Host 卡支持的电压范围。这是初始化流程中第一步协商的响应。

| 响应类型 | 长度 | 用在什么命令 | 关键数据 |
|---------|------|-------------|---------|
| R1 | 48 bits | CMD13、CMD6、CMD7 | 32 位状态字 |
| R2 | 136 bits | CMD2、CMD9、CMD10 | 128 位 CID/CSD 寄存器 |
| R3 | 48 bits | CMD1 | 32 位 OCR |

### 数据是怎么传的

不带数据的命令（如 CMD13 查状态）只有 CMD 线上的交互：

```
CMD:  ───[CMD13]──────[R1 响应]────────────
DAT:  ─────────────────────────────────────  (空闲)
```

带数据的命令在 CMD 交互后，还要在 DAT 线上传输数据块：

**单块读（CMD17）：**

```
CMD:  ───[CMD17]──────[R1]─────────────────
DAT:  ────────────────[数据块(CRC16)]──────
```

**多块读（CMD18）：**

```
CMD:  ───[CMD18]──────[R1]───────────────────[CMD12(停止)]──[R1]──
DAT:  ────────────────[数据块1][数据块2]...[数据块n]──────────────
```

多块写（CMD25）比读多一个流程——每写一块后 eMMC 会在 DAT0 上拉低表示 busy：

```
CMD:  ───[CMD25]──────[R1]──────────────────────────
DAT:  ──────[数据块1]──(busy)──[数据块2]──(busy)──
```

每个数据块的格式：

```
DAT 线: [起始位(0)] [数据(512B)] [CRC16(2B)] [结束位(1)]
```

> **这些细节为什么有用？** 调试 `data_crc_err` 时，知道每个数据块尾巴上有 2 字节 CRC16，就能理解为什么 CRS 错误一定意味着数据传输阶段出了位翻转，而不是命令阶段的问题。同样，知道多块写有 DAT0 busy，就能理解为什么内核需要 `MMC_CAP_WAIT_WHILE_BUSY` 这个 cap。

### 总线模式切换

初始化阶段 CMD 线工作在 **开漏（Open Drain）模式**——多个设备可以同时拉低 CMD 线来响应。一旦选中卡后，切换到 **推挽（Push-Pull）模式**——速度更快。

```
初始化阶段: CMD = Open Drain (多个设备竞争总线)
选中后:     CMD = Push-Pull (单设备通信)
```

这个切换由 `SDMMC_POWER` 寄存器控制。内核代码中能看到 `mmc->ios.bus_mode = MMC_BUSMODE_OPENDRAIN` 和 `MMC_BUSMODE_PUSHPULL` 的切换。
